# QUI-852 Findings: GPU SA Kernel Occupancy

## 1. Change

One block/threadgroup per replica now runs 256 cooperating threads (CUDA
`_THREADS_PER_REPLICA`, Metal `_SA_THREADGROUP_WIDTH`, clamped to the
pipeline maximum) that parallelize the O(n) local-field reduction; spin
updates remain strictly sequential on thread 0. Proposal order, acceptance
rule, and RNG consumption are unchanged; only float summation order in the
local field differs. The Metal gibbs pipeline is out of scope and keeps one
thread per replica.

## 2. Correctness evidence (CUDA, RTX 4090)

- Trajectory gate: 120 integer-coefficient records (2 domains x {64,256} x
  30 seeds, num_reads=1) — bit-identical to the shipped kernel ("OK: all
  120 trajectory records bit-identical"). Integer sums are exact in any
  order, so this gate proves the sequential semantics survived the
  parallelization.
- Distribution parity (gaussian instances): n256 base/new mean=-1528.85
  std=17.81 | n1024 base/new mean=-12398.05 std=37.38. Best energies agree
  to ~2.5e-15 relative (max, 19/20 records differing at ulp level; prints
  as dmean 0.00% under 2-decimal rounding). This drift confirms the new
  reduction path executed, while the integer-instance trajectory gate
  above (bit-identical) proves no Metropolis decision flipped.

## 3. Performance (CUDA, RTX 4090)

| case | shipped | parallel reduction | speedup |
|---|---|---|---|
| maxcut n=512 (200 reads, 2000 sweeps) | 25.5 s | 2.2 s | 11.7x |
| gaussian n=4096 (200 reads, 2000 sweeps) | 2251.0 s | 46.2 s | 48.7x |

Small-n sanity (review follow-up on !92): the 256-wide launch pays
`log2(width)` block-wide barriers per spin per sweep, so a small-model
regression was plausible. Measured against the true shipped single-thread
kernel (extracted from the pre-change revision), maxcut spin instances,
200 reads / 2000 sweeps / seed 42, RTX 4090:

| n | shipped | this MR | speedup |
|---|---|---|---|
| 32 | 0.108 s | 0.100 s | 1.08x |
| 64 | 0.355 s | 0.206 s | 1.72x |
| 128 | 1.910 s | 0.433 s | 4.41x |
| 256 | 6.900 s | 0.899 s | 7.67x |
| 512 | 27.029 s | 2.254 s | 11.99x |

No regression at any size: the reduction pays for itself from n=32 up
(parity within noise there, monotonically growing win beyond). Best
energies were identical at every size (integer coefficients, same
trajectories). Note for future re-measures: dispatching the *new* kernel
at width 1 is not a faithful shipped baseline on CUDA — it pays the
barrier overhead the shipped kernel never had (36.3 s vs 27.0 s at
n=512) and overstates the speedup; compare against the pre-change
kernel itself.

Baseline context: QUI-704 measured ~618-670 s per n=4096 solve; QUI-167
found CUDA ~5x slower than SolverDWaveCPU at MaxCut 512. Our n=4096
baseline of 2251.0 s is not directly comparable to the QUI-704 figure — the
instance generator and edge density differ between the two harnesses — so
treat it as a self-consistent before/after reference for this change only,
not as a like-for-like restatement of the QUI-704 number.

## 4. Metal status

MSL kernel mirrors the CUDA design (threadgroup reduction, barriers,
thread-0 sequential updates). Verified structurally via the mocked suite
(dispatch width, unchanged buffer ABI) and, during !92 review, numerically
on Apple hardware: the full `pytest -m metal` suite passed on an M4 Pro
(16 tests, including `test_reduction_consistency_integer_n512`, which
asserts integer-exact kernel/host energy agreement at n=512). Review-time
before/after on the M4 Pro (same params/generators as the CUDA table;
width-1 dispatch of the same kernel as baseline, which degrades the strided
loop to the shipped sequential sum):

| case | width 1 | width 256 | speedup |
|---|---|---|---|
| maxcut n=512 (200 reads, 2000 sweeps) | 45.70 s | 3.26 s | 14.0x |
| gaussian n=4096 (200 reads, 2000 sweeps) | 3026.67 s | 93.15 s | 32.5x |

The committed harness (`scripts/bench_occupancy.py`) currently drives
`SolverCudaGPU` only; adding a `--solver` flag to trajectory-gate Metal on
Apple hardware is a follow-up.

### Small-n crossover (Metal, M5 Pro)

Review asked where the reduction stops paying for itself: every solve now
launches the full-width threadgroup and pays log2(width) barriers per spin
per sweep, so tiny models could regress. Measured on an M5 Pro (maxcut spin
instances, 200 reads, 2000 sweeps, best of 3, width 1 forced by clamping
`_SA_THREADGROUP_WIDTH`):

| case | width 1 | width 256 | speedup |
|---|---|---|---|
| maxcut n=32 | 0.107 s | 0.144 s | 0.74x |
| maxcut n=64 | 0.414 s | 0.290 s | 1.43x |
| maxcut n=128 | 1.629 s | 0.589 s | 2.77x |
| maxcut n=256 | 6.741 s | 1.254 s | 5.38x |
| maxcut n=512 | 27.087 s | 2.788 s | 9.71x |

Breakeven sits between n=32 and n=64. Below that the regression is ~37 ms
absolute for a full 200x2000 solve, so no width heuristic is added — the
constant-width dispatch keeps the kernel and tests simple, and the worst
case is negligible in wall-clock terms.
