## 1. `EQUALITY`'s model register: charge sizing, fault identity, and
   register order all diverge between the two VMs — CLOSED BY !133, DO NOT FILE

**Status: closed by !133** (`e45acd1`), which lands all three parts. The
finding is kept below as the record of what was wrong and how it was
verified; the line numbers cited are this branch's original base, not
`main`.

**Evidence:** `xqvm/src/vm.rs:2542-2598` (`exec_equality`) vs.
`xqvm_py/executor.py:1309-1344` (`_runner_EQUALITY`) and
`xqvm_py/xqmx.py:525-559` (`expand_equality`).

Three distinct, verified divergences live in the same instruction:

**a. Charge sizing for a `Sample` in the model register differs.** Rust
peeks the model with `match self.reg(model) { RegVal::Model(m) => m.size,
_ => 0 }` (`vm.rs:2553-2556`) — a `Sample` sizes to `0`. Python peeks with
`current_size = peeked_model.size if isinstance(peeked_model, XQMX) else 0`
(`executor.py:1331-1332`) — `XQMX` is the single dataclass both `Model` and
`Sample` are instances of (`xqvm_py/xqmx.py:62-82`, distinguished only by a
`mode` field), so a `Sample` contributes its *real* size. Against a model
growth close to the budget, the two VMs can charge different amounts for
the same program and disagree on whether `MemoryLimitExceeded` fires.

**b. A `Sample` in the model register mutates before it faults, with a
different fault identity than Rust's.** Verified by direct execution
(script below): with a `Sample(mode=SAMPLE, size=4)` in `r0` and
`indices=[10]`, Python's `_runner_EQUALITY` writes
`model.size = max(model.size, needed)` (`executor.py:1343`) — mutating the
sample's `size` field from 4 to 11 — *before* `expand_equality` reaches its
`require_model_mode(model, "EQUALITY")` guard (`xqmx.py:539`) and raises
`XQMXModeError`. Rust never touches the sample: `as_model_mut()`
(`vm.rs:2585-2592`) rejects it immediately with `RegisterType` (mapped to
`Fault::TypeMismatch`), and `XQMXModeError` maps to a different fault,
`Fault::XqmxMode` (`conformance/src/lib.rs:435`). So for this input both
VMs fault, but with different fault identities, and only Python leaves a
mutated side effect behind first. (The original description of this
finding claimed Python "runs to completion" — that is not what happens;
confirmed by running the program in-process. The mutation-before-fault and
the fault-identity mismatch are the real, verified bugs.)

  ```python
  # Reproduction (run from the repo root):
  from xqvm_py.executor import Executor
  from xqvm_py.xqmx import XQMX, XQMXMode, XQMXDomain
  from xqvm_py.program import Program, Instruction
  from xqvm_py.opcodes import Opcode
  # r0 <- Sample(size=4); r1 <- [10]; r2 <- [1]; EQUALITY r0 r1 r2
  # raises XQMXModeError, but sample.size is already 11 by then.
  ```

**c. The two VMs check the vec length and the model's type in opposite
order.** Rust resolves and clones `indices`/`coeffs` as `vec<int>`, checks
`idx_vec.len() != coeff_vec.len()` (`vm.rs:2577-2584`), and only *then*
calls `as_model_mut()` (`vm.rs:2585-2592`) — a length mismatch is caught
before the model register is ever examined. Python resolves the model
register (`_get_register_as_xqmx`, `executor.py:1341`, which accepts a
`Sample` too) and mutates `model.size` *before* `expand_equality`'s length
check (`xqmx.py:541-543`) ever runs. Confirmed by execution: a program with
`r0` holding a plain int (not an `XQMX`) and `indices`/`coeffs` of
mismatched length raises `TypeMismatch` on Python (model check fires
first) where Rust raises `VecLengthMismatch` (length check fires first) —
a genuine, consensus-relevant fault-identity divergence.

  (Earlier drafts of this review also claimed "`_runner_EQUALITY` has no
  vec-length check at all." That claim is false: `expand_equality` already
  checks `len(indices) != len(coeffs)` and raises `VecLengthMismatch`
  (`xqmx.py:541-543`), confirmed by running a mismatched-length program
  through `xqvm_py` — it does raise `VecLengthMismatch`. The real bug is
  the *ordering* relative to the model-type check described in (c), not a
  missing check.)

**Why out of scope for QUI-1178:** none of this is a pop-before-register-
read defect — pops already precede the register reads in the fixed
`_runner_EQUALITY`. It is a set of separate register-order and
type-acceptance divergences between the two VMs' `EQUALITY` handlers.

## 2. A `vec<xqmx>` in `EQUALITY`'s or `ATLEASTW`'s index/coefficient
   registers crashes Python outside the fault system

**Evidence:** `xqvm_py/executor.py:537-542` (`_get_register_as_vec` accepts
any `Vec`, not just `vec<int>`) vs. Rust's `as_vec_int`
(`xqvm/src/value.rs:206-214`), which only accepts `RegVal::VecInt`.

Verified by direct call: `expand_equality(model, [xqmx_instance], [1], 0,
1)` raises a bare `TypeError: '<' not supported between instances of
'XQMX' and 'int'` from `XQMX.add_linear`'s bounds check `if i < 0 or i >=
self.size` (`xqvm_py/xqmx.py:196`) — not an `XQVMError` subclass, so the
conformance harness's Rust-side error mapping has nothing to catch. (The
original description guessed the crash comes from using `XQMX` values as
unhashable dict keys — `XQMX` is indeed an `eq=True` dataclass with
`__hash__ = None`, but that path is never reached: the plain `<` comparison
in the bounds check fails first. The conclusion — an unmapped Python
exception escapes the fault system — is confirmed either way.)

`ATLEASTW` has the same exposure: `weight_sum = check_i64(weight_sum + w,
...)` (`xqvm_py/executor.py:1399`) raises `TypeError: unsupported operand
type(s) for +` when `w` is an `XQMX` pulled from a `vec<xqmx>` coeffs
register.

**Why out of scope for QUI-1178:** register-content validation, not
pop/charge ordering.

## 3. Rust's `EQUALITY` charge-sizing narrows before charging — live on
   64-bit hosts too, not just wasm32

**Evidence:** `xqvm/src/vm.rs:2542-2550`:

```rust
let (n_terms, needed) = match self.reg(indices) {
    RegVal::VecInt(v) => (
        v.len(),
        v.iter()
            .max()
            .and_then(|&max_idx| max_idx.checked_add(1))
            .and_then(|needed| usize::try_from(needed).ok())
            .unwrap_or(0),
    ),
    _ => (0, 0),
};
```

The first link in this chain, `.and_then(|&max_idx| max_idx.checked_add(1))`
(`vm.rs:2547`), already fails before the target-width narrowing on the next
line ever runs: `indices` is a `vec<i64>`, so an `indices` vector containing
`i64::MAX` makes `checked_add(1)` overflow `i64` and return `None` —
`usize::try_from` is never reached. `.unwrap_or(0)` then sizes the model
growth to zero, no charge is raised, and `exec_equality` proceeds past the
charge to `indices_to_usize` (`vm.rs:2591`), which raises
`IndexOutOfBounds` against the tiny (or zero-grown) model. This is a plain
`i64` overflow, so it reproduces identically on a 64-bit host and on
wasm32 — the `usize::try_from` step that follows is a second, narrower
hazard specific to a 32-bit `usize` (an index at or above `u32::MAX` with
no `i64::MAX` involved), but it is not the only way into this bug, and not
the one that matters on the reference target.

Python's `needed` is an unbounded Python int (`executor.py:1330`) with no
equivalent overflow, so for the same `indices=[i64::MAX]` input it charges
`needed` (~8 EiB) and raises `MemoryLimitExceeded`, while Rust — on the
64-bit reference VM as well as the wasm32 chain target — silently charges
zero and raises `IndexOutOfBounds` instead. Same divergence class as the
wasm32-only framing this section previously used, but reachable without a
32-bit target at all.

`xqvm/src/vm.rs:807-824` (`Vm::allocation_size`) already documents and
implements the correct pattern for exactly this hazard: charge off the
`i64`/`u64` value *before* narrowing to `usize`, specifically "including
... the wasm32 runtime ... where `usize::try_from` would otherwise decide
the answer." `exec_equality` does not follow its own codebase's documented
pattern, and the fix needs to charge off the pre-`checked_add` value, not
just swap the narrowing step for a wider one.

**Why out of scope for QUI-1178:** not a pop/charge-ordering defect within
one VM; it is a target-independent charge-sizing bug in Rust alone that
happens to also have a second, wasm32-specific manifestation.

**Severity: fix-soon, not release-gating. It is not exploitable.** Traced
end to end before filing, so whoever picks this up does not have to treat
it as a security incident:

- The skipped charge is for growth that also never happens. `needed` sizes
  to `0`, so `if needed > m.size` is false, the model never grows, and
  `indices_to_usize` then always fails. No unpriced allocation, no state
  change; `charge_equality_expansion` still fires, so the expansion stays
  priced.
- It cannot go the other way. For the narrowing to be swallowed, `max_idx`
  must exceed anything `m.size` could reach, so there is no input where
  wasm32 succeeds and a 64-bit host faults.
- It is not a consensus hazard. All consensus execution is the same wasm
  blob, so every validator reaches `IndexOutOfBounds` together.

What it costs is developer trust: `xquad run` natively reports
`MemoryLimitExceeded` where the chain reports `IndexOutOfBounds` for the
same program. The reason to fix it anyway is that the fix is three lines
against a pattern already in the same file, and `allocation_size`'s
docstring is normative — one unfixed violation beside it is how that
invariant stops being true.

**The test gap is worth more than the fix.** No test in the repo can
observe this class: `make conformance` and `test-substrate-fixture` both
run natively, and `test:wasm` builds `wasm32v1-none` but its fixture
(`fixtures/xqvm-wasm/src/lib.rs`) holds five smoke tests — push/add/halt,
calldata, roundtrip, stack underflow — none touching allocation or index
narrowing, and the job is path-gated so it usually does not run. A sweep of
`vm.rs` found 28 `usize::try_from` sites, 27 of which turn a failed
narrowing into a fault with identical identity on both targets, plus two
`(i64::BITS - leading_zeros) as usize` expressions bounded by 64 — so this
is currently the only instance. Nothing would report a second one.

## 4. `EXCLUDE` and `IMPLIES` charge unconditionally in Rust, conditionally
   in Python — FIXED IN FLIGHT BY !133, DO NOT FILE

**Evidence:** `xqvm/src/vm.rs:2470` (`exec_exclude`) and `:2498`
(`exec_implies`) both call `self.charge(pos, ...)` directly, charging
regardless of what the register holds. Python's `_runner_EXCLUDE`
(`executor.py:1296`) and `_runner_IMPLIES` (`executor.py:1305`) instead
call `self._charge_coefficient(reg, ...)`
(`executor.py:463-476`), which charges only `if isinstance(value, XQMX) and
value.is_model()` — nothing is charged for a `Sample` or an unset/wrong-kind
register.

**Failure scenario:** a tight budget with a `Sample` register in `r0`:
`EXCLUDE r0` raises `MemoryLimitExceeded` on Rust (it charges
unconditionally) and does not on Python (charges nothing, then faults on
`_get_register_as_xqmx`'s wrong-mode check further down, or succeeds if
the register happens to be model-shaped enough elsewhere) — a fault
divergence driven purely by register kind.

**Why out of scope for QUI-1178:** `_charge_coefficient` already precedes
the register read in both runners — the pop/charge/read order this ticket
fixes is already correct here. The bug is which existing helper Python
calls (`_charge_coefficient`, conditional) versus what Rust actually does
(`charge`, unconditional), not the order of operations.

**Status: closed by !133** (`feature/qui-1062-1029-1174`), which replaces
both calls with an unconditional `self._charge(...)` ahead of the register
read. Kept here as a record of the finding; no ticket needed. If !133 is
ever reworked or dropped, this becomes live again.

## 5. `SETQUAD`/`ADDQUAD`/`GETQUAD` type-check more loosely in Python than
   in Rust

**Evidence:** Rust's `exec_get_quad`/`exec_set_quad`/`exec_add_quad`
(`xqvm/src/vm.rs:2055-2062`, `:2077-2085`, `:2104-2112`) all resolve the
register with `as_model()`/`as_model_mut()`, which reject a `Sample`.
Python's counterparts (`_runner_GETQUAD`/`_runner_SETQUAD`/`_runner_ADDQUAD`,
`executor.py:1133-1158`) all call `_get_register_as_xqmx`
(`executor.py:544-549`), which accepts both `Model` and `Sample`.

(By contrast, `GETLINE`/`SETLINE`/`ADDLINE` are *not* part of this finding:
Rust's `as_xqmx_grid`/`as_xqmx_grid_mut` for those three explicitly accept
`model|sample`, matching Python.)

**Failure scenario:** `SETQUAD r0 ...` with a `Sample` in `r0` succeeds on
Python (mutating the sample's `quadratic` map) and raises `RegisterType`
("expected model, got sample") on Rust.

**Why out of scope for QUI-1178:** a register-type-acceptance divergence,
not a pop/charge/read ordering defect.

## 6. `require_model_mode` in `ATLEAST`/`ATLEASTW` has no direct Rust
   counterpart — open spec question

**Evidence:** `xqvm_py/executor.py:1367` and `:1407` call
`require_model_mode(model, ...)` explicitly. Rust's `exec_at_least`
(`vm.rs:2646-2653`) and `exec_at_least_w` have no equivalent explicit call
— but this is because Rust's `RegVal` splits `Model` and `Sample` into
separate enum variants (`xqvm/src/value.rs:119-131`), so `as_model_mut()`
already excludes a `Sample` at the type level; there is no separate "mode"
to check. Python's single `XQMX` dataclass conflates both under one type
with a `mode` field, so `_get_register_as_xqmx` (which accepts either)
needs the extra `require_model_mode` call to reject a `Sample` the same
way Rust's type system does structurally.

Whether this makes Python's explicit checks in `ATLEAST`/`ATLEASTW`
correct patches for a real gap (and `EQUALITY`, item 1, is the one still
missing its patch), or whether the whole `_get_register_as_xqmx` accepting
`Sample` in these grid/coefficient opcodes is itself the wrong design, is a
spec question, not a reorder.

**Why out of scope for QUI-1178:** design/spec decision, not an ordering
defect.

## 7. `conformance::Inputs` cannot express a memory limit

**Evidence:** `conformance/src/lib.rs:74-99` — `Inputs` carries `calldata`,
`output_slots`, and `step_limit`, with no `memory_limit` field.

Several of the route-B fault-ordering cases this branch introduced are
only reachable against a near-exhausted allocation budget (the
`MemoryLimitExceeded` row in `conformance/README.md`'s new "Fault ordering
(QUI-1178)" table: `VECPUSH`, `SETLINE`, `ADDLINE`, `SETQUAD`, `ADDQUAD`,
`EXCLUDE`, `IMPLIES`, `REDUCE`). Without a `memory_limit` field on
`Inputs`, cases that need a *small*, deliberately tight budget (rather
than a program engineered to overflow the default) can only be pinned as
per-VM unit tests (`xqvm_py/tests/test_executor.py::TestFaultOrdering`),
not as shared conformance vectors that exercise both runtimes identically.

**Suggested fix:** add `memory_limit: Option<u64>` (or a sentinel
"unset = default") to `Inputs`, plumbed to `Vm::set_memory_limit` on the
Rust side and to a `--memory-limit` flag on `python -m xqvm_py run` on the
Python side.

**Why out of scope for QUI-1178:** harness/tooling gap, not a runner bug.

## 8. An unset register produces different fault identities depending on
   which accessor the opcode uses

**Evidence:** Python's `_get_register_as_vec`/`_get_register_as_xqmx`
(`executor.py:537-549`) both call `self.state.get_register(slot)`, which
raises `RegisterNotFound` (`xqvm_py/state.py:244-246`) for an unset slot —
mapped to `Fault::UnsetRegister` (`conformance/src/lib.rs:424`).

Rust already has a helper that discriminates this correctly —
`Vm::require_vec`/`Vm::require_vec_int` (`vm.rs:895-921`) explicitly match
`RegVal::Unset` to `Error::UnsetRegister`, as the surrounding doc comment
says in as many words: *"folding 'never written' into the type arm makes
an unset register a `TypeMismatch` here and an `UnsetRegister` there."*
But `require_vec_int` is used by exactly one opcode, `SLACK`
(`vm.rs:1881-1882`) — `exec_equality`, `exec_at_least`, and
`exec_at_least_w` all resolve their vec registers directly through
`self.reg(...).as_vec_int()` (e.g. `vm.rs:2559-2576`), which does not
discriminate `Unset` and maps it to `Error::RegisterType` →
`Fault::TypeMismatch` instead. The same applies to `as_model_mut` for the
model register in these same opcodes and in `SETQUAD`/`ADDQUAD`/`GETQUAD`.

**Failure scenario:** `EQUALITY r0 r1 r2` with `r1` (indices) never
written raises `UnsetRegister` on Python and `TypeMismatch` on Rust.

**Why out of scope for QUI-1178:** VM-wide accessor inconsistency (some
opcodes already use the discriminating `require_vec`/`require_vec_int`
helper; most don't), not specific to the 22 opcodes this ticket reordered,
and not a pop/charge/read ordering defect.

## 9. The `test_pops_precede_the_register_read` AST guard can be defeated
   into silence, not into a false alarm

**Evidence:** `xqvm_py/tests/test_executor.py:3186-3221`
(`TestFaultOrdering._first_positions` and `REGISTER_READS`).

The guard walks each runner's AST, takes the source position of its first
call to `_get_register_as_xqmx`/`_get_register_as_vec` and the position of
its first call to `.pop()`/`.pop_n()`, and fails only when a read's
position is earlier than a pop's (`min(reads) < min(pops)`, in effect,
via `test_pops_precede_the_register_read`'s `read < pop` check). A prior
draft of this document described the guard's weakness as a *false hit* —
the guard incorrectly flagging correct code. That has the risk direction
backwards: because the check only ever compares the *first* read against
the *first* pop, everything that can go wrong with it makes the guard
under-report, silently passing a runner that violates the ordering the
spec requires. Three distinct ways to do that, none hypothetical:

1. **A `.pop()`/`.pop_n()` call on something that is not the operand
   stack, executed before the register read.** The guard matches on
   method name alone (`name in TestFaultOrdering.POPS`, keyed off
   `ast.Attribute.attr` or a bare identifier), not on the receiver. Any
   call named `pop`/`pop_n` anywhere in the runner — on a list, a dict, a
   local collection — lowers `min(pops)` below the register read's
   position and the runner passes, even though not one operand was
   actually popped off the VM stack first.
2. **A real stack pop, then the register read, then more stack pops.**
   The guard only compares the *first* pop's position to the *first*
   read's position. A runner that pops one operand, reads a register, and
   then pops its remaining operands has `min(pops) < min(reads)` and
   passes, even though the register read still runs before the operand
   stack is fully drained — exactly the ordering the spec forbids for any
   operand popped after that read.
3. **A register read through an accessor the guard does not know about.**
   `REGISTER_READS` hardcodes accessor method names, so a runner
   calling `self.state.get_register(...)` directly, or reaching a register
   through an accessor absent from that set, reads a register in
   a way the guard's `ast.walk` never recognizes as a "read" at all —
   `min(reads)` stays `None`, `_first_positions` returns no read position,
   and `test_pops_precede_the_register_read`'s `if read is not None and
   pop is not None and read < pop` guard clause skips the runner (neither
   branch of the `and` is true), so it is silently exempt rather than
   flagged.

The third was live when this was first written: `_get_register_as_model`
exists on `main` and `EQUALITY`/`ATLEAST`/`ATLEASTW` resolve their model
register through it. `REGISTER_READS` now lists it and
`_get_register_as_int` alongside the two vec/xqmx accessors, so the set is
the whole accessor family rather than a subset — but it is still a
hardcoded list, and a new accessor added without a matching entry is
silently exempt again. Blind spots 1 and 2 are untouched.

None of the three currently escapes the guard in `xqvm_py/executor.py`, confirmed
by direct inspection rather than assumed: every `.pop(`/`.pop_n(` call in
the file is `self.state.pop(...)`/`self.state.pop_n(...)` (the operand
stack, not some other object) and — separately — no runner interleaves a
pop after a register read today; no runner bypasses the `_get_register_as_*` helpers to call
`self.state.get_register(...)` directly. The guard's blind spots are latent, not yet triggered.

**Why out of scope for QUI-1178:** a test-harness gap in the invariant
guard added by this ticket, not an ordering defect in a runner it
currently covers.

## 10. `ONEHOTR`/`ONEHOTC` size their charge off a sample the Python runners
   accept — FIXED IN !134, QUI-1202

**Found in review of !134, 2026-08-28, filed as
[QUI-1202](https://linear.app/quip-network/issue/QUI-1202) and then fixed
in the same MR. Kept as the record of what was wrong; do not file it
again.** The fix adds `_peek_model_grid` (`xqvm_py/executor.py`) and moves
both ONEHOT runners to peek, charge, then `_get_register_as_model`. Pinned
by `TestFaultOrdering::test_onehot_does_not_charge_for_a_sample`.

The `EQUALITY` analogue is finding 1a, which !133 closed with
`_peek_model_size`. `ONEHOTR`/`ONEHOTC` were not part of that fix, which is
why this survived the rebase.

**Evidence:** `exec_one_hot_r` (`xqvm/src/vm.rs:2480-2493`) sizes the
charge from a peek — `match self.reg(reg) { RegVal::Model(m) => m.cols, _
=> 0 }` — takes `charge_equality_expansion`, and only then resolves the
register with `as_model_mut`, which rejects a `Sample`. So a sample
charges nothing and raises `RegisterType`.

`_runner_ONEHOTR`/`_runner_ONEHOTC` (`xqvm_py/executor.py:1341-1371`) have
no peek at all. Both go pop, `_get_register_as_xqmx` (which accepts a
`Sample`, `executor.py:611-616`), dimension check, then charge — so a
sample's real `rows`/`cols` size the charge.

**Failure scenario:** with a 3x3 `BSMX` sample in `r0` and a budget with no
headroom past the setup, `xqvm_py` raises `MemoryLimitExceeded` (240 bytes
against a 72-byte budget) where the Rust VM charges nothing and raises
`RegisterType` (`TYPE_MISMATCH`). Confirmed by running the program below
through both VMs.

At a generous budget the same program diverges for a second, separate
reason: Python raises `XQMXModeError` (`Fault::XqmxMode`) where Rust
raises `RegisterType` (`Fault::TypeMismatch`). **That one is not part of
this finding and was not fixed.** `spec/xqvm/SPEC.md:211` records
`XqmxMode` as the one unresolved row in the fault table — either identity
is defensible until the question is settled, and no vector may assert
either. What the fix removes is the budget's ability to change the answer:
the same fault now comes out at any budget, as it does on Rust.

**The verifier admits it, two ways.** `check_reads` requires `R::Model` for
`OneHotR`/`OneHotC` (`xqvm/src/verifier/reg_type.rs:186-190`), so a
register the verifier knows is a `Sample` is rejected statically. It does
not always know.

**Route 1 -- host calldata.** `Vm::set_calldata` (`xqvm/src/vm.rs:400`)
accepts any `RegVal`, samples included, and says so; `exec_input` clones
the entry into the register. `INPUT` writes `RegType::Any`, which
satisfies every requirement, so `PUSH 0 / INPUT r0 / PUSH 0 / PUSH 1 /
ONEHOTR r0` verifies clean and arrives holding whatever the embedder put
in slot 0. The `--calldata` CLI flag parses i64s and cannot express it,
which is what makes this easy to miss from the command line; the embedding
API is the reachable surface, and on a chain runtime the host fills those
slots. Confirmed post-fix with a 3x3 `binary_sample` in slot 0: the same
`XQMXModeError` at a 72-byte budget and at 2^30.

**Route 2 -- a branch join.** `meet_reg` merges two different concrete
types to `RegType::Any` (`xqvm/src/dataflow/register.rs:95-101`) and `Any`
satisfies every requirement (`reg_type.rs:69-72`), so a branch that writes
`BQMX` on one path and `BSMX` on the other joins to `Any` and verifies
clean using only its own instructions:

  ```asm
  PUSH 0
  INPUT r1
  LOAD r1
  JUMPI .0
  PUSH 9        ; selector == 0: r0 is a SAMPLE
  BSMX r0
  JUMP .1
  .0:
  PUSH 9
  BQMX r0
  .1:
  PUSH 3
  PUSH 3
  RESIZE r0
  PUSH 0
  PUSH 1
  ONEHOTR r0
  HALT
  ```

  `xquad verify --text` accepts this. `xquad run --text --calldata 0
  --memory-limit 80` raises `register r0 holds sample, expected model`.
  The same program on `xqvm_py` raised `MemoryLimitExceeded` before the
  fix and raises `XQMXModeError` at any budget after it.

**Fix as landed:** `_peek_model_grid` is the `(rows, cols)` twin of
`_peek_model_size`, gated on `is_model()`. Both runners now peek, charge
bytes and steps, then resolve with `_get_register_as_model`. The explicit
`rows == 0 or cols == 0` check went with it: `row_indices`/`col_indices`
raise the same `InvalidGridDimensions` through `grid_row_extent`, and
placing it after the charge is what `exec_one_hot_r` does (`grid_row_index`
follows `charge_equality_expansion`).

**Still open, deliberately:** whether Rust's peek should read `cols` off a
grid rather than a model is the same design question as finding 6, and the
`XqmxMode` naming question above is SPEC.md:211's. Neither is touched.
