# QUI-167: MaxCut & TSP Scale Sweep — Findings

**Ticket:** [QUI-167](https://linear.app/quip-network/issue/QUI-167) · **Date:** 2026-07-13 ·
**Harness:** `scripts/scale_sweep.py` (commit `853de8e`) · **Machine:** linux x86_64 (WSL2),
RTX 4090, Python 3.13, xquad @ `10b062d` (post-v0.3.0 main)

134 records, 6 lanes, 3 seeds per rung, 300 s per-point timeout. Raw data:
`scratch/scale_sweep/results.jsonl` (not committed; regenerate the summary with
`render_report`). **Zero verifier-invalid and zero structurally-invalid solutions across all
132 ok points.**

## Lane ceilings

| problem | backend | solver | max n |
|---|---|---|---|
| maxcut | python | dwave-cpu | 512 |
| maxcut | rust | cuda-gpu | 512 |
| maxcut | rust | dwave-cpu | 512 |
| tsp | python | dwave-cpu | 48 |
| tsp | rust | cuda-gpu | 32 |
| tsp | rust | dwave-cpu | 48 |

All four CPU lanes completed their **full ladders** (MaxCut 512 = 512 vars; TSP 48 = 2304
vars) with zero timeouts — every ceiling above except tsp/cuda is the end of the ladder, not
a resource limit. The two real ceilings found:

- **maxcut/rust/cuda-gpu n=1024 → `error` in `encode`: `StepLimitExceeded { limit: 10000000 }`.**
  The first hard XQVM scale limit observed. MaxCut n=1024 has ~524k edges; the encoder's
  per-edge loop exceeds the Rust interpreter's 10M-step cap. Not GPU-related — any backend
  would hit it at this size. The VM step budget, not time or memory, is the binding
  constraint for encoder-loop-heavy programs.
- **tsp/rust/cuda-gpu n=48 → `timeout` (>300 s) in `solve`.** GPU solve time roughly
  triples per TSP rung (2.45 s @ n=12 → 104 s @ n=32), putting n=48 (~310+ s) past the cap.

## Stage breakdown at the largest common rungs

MaxCut n=512 (512 vars) and TSP n=48/32 (2304/1024 vars), median of 3 seeds, seconds:

| problem | backend | solver | n | vars | compile | encode | solve | verify | decode | peak MiB |
|---|---|---|---|---|---|---|---|---|---|---|
| maxcut | python | dwave-cpu | 512 | 512 | 0.002 | 2.957 | 4.957 | 0.016 | 0.002 | 112 |
| maxcut | rust | dwave-cpu | 512 | 512 | 0.002 | 0.908 | 4.928 | 0.173 | 0.001 | 142 |
| maxcut | rust | cuda-gpu | 512 | 512 | 0.002 | 0.904 | 26.164 | 0.184 | 0.001 | 328 |
| tsp | python | dwave-cpu | 48 | 2304 | 0.002 | 1.070 | 6.114 | 0.020 | 0.001 | 129 |
| tsp | rust | dwave-cpu | 48 | 2304 | 0.002 | 0.540 | 5.985 | 0.290 | 0.001 | 165 |
| tsp | rust | cuda-gpu | 32 | 1024 | 0.002 | 0.150 | 104.173 | 0.087 | 0.000 | 294 |

Observations:

1. **Solve dominates every CPU lane at scale**; compile and decode are negligible
   throughout. Encode grows ~O(n²) with problem size and is the second-largest cost.
2. **Rust VM encodes ~2–3.3× faster than the Python VM** at the top rungs (0.908 s vs
   2.957 s on MaxCut 512). Smaller than expected — both are bound by per-step interpretation
   of the same instruction stream.
3. **Anomaly — Rust VM `verify` is ~10–15× slower than Python VM `verify`**
   (0.173 vs 0.016 s on MaxCut 512; 0.290 vs 0.020 s on TSP 48), consistently across all
   rungs. Verify is dominated by XQMX energy evaluation; the Rust path likely pays per-call
   FFI overhead on model/sample access. Candidate follow-up ticket.
4. **Memory is a non-issue** at these sizes: peak RSS 328 MiB (GPU lanes carry a ~260 MiB
   CUDA-runtime baseline; CPU lanes stay under 165 MiB).

## Cross-VM parity (python vs rust, dwave-cpu)

- **MaxCut: deterministic — 0 mismatches** across all 21 common points up to n=512.
- **TSP: 15/24 points diverge (all n≥8).** Investigated: the decoded tours differ *and*
  their energies differ (within ~1.5%, neither VM systematically better; e.g. n=48 seed=42:
  python −8737/dist 863 vs rust −8855/dist 745). Every solution remains verifier-valid and
  structurally valid, and each VM's energy is consistent with its own tour's recomputed
  distance — so the two VMs are **semantically equivalent** and this is **not** a
  QUI-465-class decode bug. Root cause: the identically-seeded `SolverDWaveCPU` receives a
  model object whose internal term ordering depends on which VM built it, which perturbs the
  stochastic anneal trajectory. Bit-for-bit cross-VM reproducibility of *samples* would
  require a canonical term ordering in XQMX before solving (or documenting that seed
  reproducibility is per-backend only). Candidate follow-up ticket.

## GPU solver (SolverCudaGPU) vs CPU (SolverDWaveCPU)

- **Slower at every size tested**: ~0.3 s fixed startup at toy sizes, ~5× slower at MaxCut
  512 (26.2 vs 4.9 s), ~50× slower at TSP 32 (104 vs 2.0 s).
- **Solution quality diverges on MaxCut at n≥32**: energy delta (GPU − CPU) grows from
  ~+300 at n=32 to **+100k–103k at n=512** (CPU cuts 3.434M–3.440M vs GPU 3.334M–3.337M;
  ~3% worse), all three seeds. On TSP the GPU is slightly *better* (deltas −17…−158 at n=24–32) while being
  far slower.
- Reading: the CUDA solver's sweep schedule does not scale with problem size the way the
  CPU solver's does — it burns its budget on many parallel chains at fixed depth. Directly
  relevant to QUI-687 (larger-model GPU validation) and QUI-704 (bit-packed spin storage);
  both should treat "sweeps-per-variable parity with SolverDWaveCPU" as the comparison
  baseline, not wall-clock alone.

## Implications for v0.3.1+

1. **VM step limit is the first scale wall** (`StepLimitExceeded` at MaxCut n=1024 encode).
   Options: configurable step budget, per-loop step accounting, or encoder-side chunking.
   Worth a ticket before anyone targets n≥1000 models.
2. **Rust-VM verify slowdown** (~10×, FFI-suspect) is the only place the Rust backend loses
   to the reference interpreter — cheap profiling target.
3. **Cross-VM sample reproducibility** needs either canonical XQMX term ordering pre-solve
   or an explicit statement that seeds reproduce per-backend only.
4. **CUDA solver quality/speed at scale** underperforms CPU on MaxCut ≥32 vars — feeds
   QUI-687/QUI-704 as above.
5. The prototype otherwise **holds up well beyond the tested envelope**: 100% valid
   solutions, no crashes, no memory pressure, full CPU ladders completed in seconds per
   point.
